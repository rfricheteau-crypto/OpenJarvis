### Analyse du problème — ce que Claude a trouvé dans le code réel

#### Cause n°1 (certaine) — Pas d'echo cancellation sur le microphone

Dans `useSpeech.ts`, ligne 185, l'accès micro est demandé ainsi :
```ts
stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```
Et ligne 551 (dans `measureAmbientLevel`) :
```ts
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```

`{ audio: true }` ne demande **aucune** suppression d'écho au navigateur.

Quand Jarvis parle (TTS via `voice_proxy_routes.py` → sidecar Kokoro/Piper → fichier `.wav` lu par le navigateur), le son sort par les haut-parleurs. Le microphone ouvert capte ce son. La VAD (`recordUntilSilence`) l'interprète comme de la parole humaine. Un nouveau cycle de transcription commence. Jarvis se transcrit lui-même. C'est la source de la "double voix" et du bug anti-écho.

**C'est la cause principale, confirmée par le code.**

---

#### Cause n°2 (probable) — Fenêtre de race entre TTS et VAD

La VAD dans `recordUntilSilence` (lignes 395–462) analyse l'audio en continu avec `requestAnimationFrame`. Elle ne sait pas si Jarvis est en train de parler. Il n'existe aucun mécanisme de coordination entre :
- le moment où le TTS envoie `/api/voice/speak`
- le moment où la VAD démarre ou est active

Si le composant appelant démarre `recordUntilSilence` immédiatement après avoir reçu une réponse TTS, et que le fichier `.wav` est encore en cours de lecture, la VAD capture le TTS. L'option `ignoreAudioUntilMs` existe (ligne 336) mais doit être passée par l'appelant — si elle n'est pas utilisée ou trop courte, l'écho n'est pas filtré.

---

#### Cause n°3 (possible) — Double appel à transcribeAudio

Dans `useSpeech.ts`, deux chemins indépendants peuvent terminer une transcription :
- `stopRecording()` (ligne 249) : déclenche `transcribeAudio()` dans son propre `onstop`
- `recordUntilSilence()` (ligne 327) : remplace `recorder.onstop` (ligne 467) et déclenche aussi `transcribeAudio()`

Si un composant appelle `stopRecording()` pendant que `recordUntilSilence()` est actif, les deux `onstop` peuvent théoriquement entrer en compétition. Le guard `activeRecordPromiseRef` (ligne 328) protège contre un second appel à `recordUntilSilence`, mais pas contre un appel externe à `stopRecording()` pendant que `recordUntilSilence` est actif.

En pratique, `onstop` est écrasé par le second setter (le dernier `recorder.onstop = …` gagne). Mais si l'appelant utilise les deux fonctions simultanément, le comportement peut être imprévisible.

---

### Solution proposée par Claude

**Fix A — Activer l'echo cancellation navigateur (priorité haute, risque faible)**

Dans `useSpeech.ts`, remplacer les deux `getUserMedia({ audio: true })` par :
```ts
getUserMedia({
  audio: {
    echoCancellation: true,
    noiseSuppression: true,
    autoGainControl: true,
  }
})
```

C'est une contrainte "hint" pour le navigateur. Si le matériel ne le supporte pas, le navigateur ignore gracieusement les contraintes non satisfaisables. Impact minimal, retour arrière trivial.

**Fix B — Utiliser `ignoreAudioUntilMs` correctement (priorité moyenne, côté appelant)**

Dans le composant qui appelle `recordUntilSilence`, calculer la durée du TTS (disponible dans `elapsed_ms` de la réponse `/api/voice/speak`) et passer `ignoreAudioUntilMs` avec une marge :
```ts
await recordUntilSilence({
  ignoreAudioUntilMs: ttsElapsedMs + 500, // +500ms de marge
});
```
Cela supprime le début de l'audio après une réponse TTS. **Nécessite de voir le composant appelant** — Claude ne l'a pas lu.

**Fix C — Ne pas appeler `recordUntilSilence` pendant que le TTS joue (priorité haute, côté architecture)**

Ajouter un état `isSpeaking: boolean` dans le composant, activé quand `/api/voice/speak` est appelé, désactivé quand la lecture audio est terminée (événement `ended` de l'élément `<audio>`). Bloquer `recordUntilSilence` si `isSpeaking` est vrai. C'est la solution propre mais elle nécessite de voir le composant.
