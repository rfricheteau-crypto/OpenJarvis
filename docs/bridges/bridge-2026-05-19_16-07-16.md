### DIAGNOSTIC GLOBAL — Révélation structurelle

**Il existe deux pipelines vocaux distincts actifs dans ce projet. Ils partagent le même sidecar TTS (port 8011) et le même endpoint STT. Aucun mécanisme ne les coordonne. C'est la cause racine de la majorité des symptômes.**

### Analyse du problème — ce que Claude a trouvé dans le code réel

#### Architecture réelle — deux pipelines vocaux qui coexistent

```
PIPELINE 1 — OpenJarvis (navigateur)
  useSpeech.ts (React hook, MediaRecorder, VAD JS manuel)
    → POST /v1/speech/transcribe (api_routes.py → faster_whisper / openai / deepgram)
    → POST /api/voice/speak (voice_proxy_routes.py → sidecar :8011)
    → navigateur joue le .wav depuis /api/voice/audio/{file}
  Anti-écho : ABSENT côté serveur. Option ignoreAudioUntilMs côté hook, non coordonnée.
  VAD : JavaScript dans le navigateur (AnalyserNode RMS)
  Voix : Kokoro → Piper → eSpeak (fallback automatique)

PIPELINE 2 — Hermès WebRTC POC V2
  hermes-webrtc-poc-v2 (pipecat, SmallWebRTC)
    → VAD SileroVAD côté serveur
    → STT via hermes_bridge.transcribe_wav() → même endpoint /v1/speech/transcribe
    → TTS via hermes_bridge.speak_kokoro() → même sidecar :8011
    → audio envoyé via WebRTC frames (pas de fichier .wav navigateur)
  Anti-écho : phases serveur (LISTENING → RECORDING → TRANSCRIBING → THINKING
              → SPEAKING → COOLDOWN → LISTENING_AGAIN)
              + POST_SPEAK_COOLDOWN_SECONDS = 1.2s
              + BARGE_IN_TRANSCRIPT_GUARD_MS = 1800ms
              + détection echo par similarité textuelle (_detect_barge_in_echo)
  VAD : SileroVAD (server-side, modèle ML dédié)
  Voix : Kokoro uniquement (strict, pas de fallback Piper dans ce pipeline)
```

Ces deux pipelines partagent : **même sidecar Kokoro port 8011, même asyncio.Lock().**

#### Cause n°1 (certaine) — Pas d'echo cancellation sur le microphone

Dans `useSpeech.ts`, ligne 185, l'accès micro est demandé ainsi :
```ts
stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```
Et ligne 551 (dans `measureAmbientLevel`) :
```ts
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```

`{ audio: true }` ne demande **aucune** suppression d'écho au navigateur.

Quand Jarvis parle (TTS via `voice_proxy_routes.py` → sidecar Kokoro/Piper → fichier `.wav` lu par le navigateur), le son sort par les haut-parleurs. Le microphone ouvert capte ce son. La VAD (`recordUntilSilence`) l'interprète comme de la parole humaine. Un nouveau cycle de transcription commence. Jarvis se transcrit lui-même. C'est la source de la "double voix" et du bug anti-écho.

**C'est la cause principale, confirmée par le code.**

---

#### Symptôme 1 — Deux voix simultanées / voix homme-femme qui changent

**Source : le sidecar TTS a une chaîne de fallback automatique.**

Dans `voice_sidecar_app.py`, la chaîne est :
```
Kokoro (ff_siwis — voix française féminine, 24000 Hz)
  → timeout 30s → Piper (fr_FR-siwis-medium — voix médium différente)
    → timeout 12s → eSpeak (fr-fr — voix synthétique robotique)
```

Si Kokoro est lent ou occupé (Lock), Piper prend le relais **avec une voix différente**. Si les deux pipelines font des appels TTS simultanés, le `asyncio.Lock()` les sérialise — le deuxième attend, puis utilise le moteur qui est disponible. Résultat : une réponse peut être lue par Kokoro, la suivante par Piper. L'utilisateur entend deux voix différentes.

De plus : si le pipeline 1 (navigateur) est actif en même temps que le pipeline 2 (WebRTC), ils peuvent tous les deux produire de l'audio quasi-simultanément, l'un via WebRTC frames, l'autre via lecture de fichier .wav dans le navigateur.

**Cause racine : deux pipelines actifs + fallback chain non contrôlée.**

---

#### Symptôme 2 — Mauvaise transcription

**Plusieurs causes superposées :**

**2a — useSpeech.ts version locale massivement modifiée**
Le commit `3b77c3e` (aujourd'hui même) montre que `useSpeech.ts` a été modifié de +600 lignes dans la version non commitée. Le `git diff` ne produit aucun output entre HEAD et l'index, ce qui signifie que la version locale non commitée n'est pas la même que le fichier committé. La version non commitée actuellement sur disque EST celle qui a été modifiée après le snapshot.

**2b — Le sidecar STT reçoit peut-être de l'audio qui inclut du TTS**
Dans le pipeline 1, si `getUserMedia({ audio: true })` est actif pendant que le TTS joue, le microphone capte le TTS. La VAD JS (RMS sur AnalyserNode) peut le détecter comme de la parole si le niveau est suffisant. Résultat : Jarvis transcrit sa propre voix.

**2c — faster_whisper : lazy-load coûteux à la première requête**
`_ensure_model()` charge le modèle à la première transcription. Sur Mac sans GPU, ce chargement peut prendre 5-30 secondes. Pendant ce temps, les requêtes STT timeout ou se comportent de manière imprévisible. La route `/v1/speech/health` interroge `backend.health()` toutes les 20s depuis le frontend (ligne 122-126 de useSpeech.ts), ce qui peut déclencher `_ensure_model()` au moment où une transcription réelle arrive simultanément.

**2d — Variables globales non thread-safe**
Dans `voice_proxy_routes.py` : `_LAST_ENGINE_USED` et `_LAST_ERROR` sont des globals Python mutables, modifiés par `_set_last_engine()` et `_set_last_error()`. Dans un serveur ASGI multi-worker, ces valeurs ne sont pas partagées entre workers. Les fonctions `_hydrate_runtime_state()` compensent partiellement en lisant le fichier JSONL, mais c'est une lecture fichier à chaque health check.

---

#### Symptôme 3 — Anti-écho instable

**La situation est asymétrique entre les deux pipelines :**

Pipeline 2 (WebRTC) a un anti-écho serveur robuste :
- Phases d'état machine (SPEAKING → COOLDOWN 1.2s → LISTENING_AGAIN)
- Guard window post-TTS de 1200ms (`BARGE_IN_ACCEPT_AFTER_AUDIO_END_MS`)
- Guard transcript 1800ms (`BARGE_IN_TRANSCRIPT_GUARD_MS`)
- Détection d'écho par similarité textuelle (`_detect_barge_in_echo`)
- `_last_audio_play_end_at` pour chronométrer précisément la fin du TTS

Pipeline 1 (navigateur, useSpeech.ts) :
- Anti-écho navigateur : ABSENT (`getUserMedia({ audio: true })` sans `echoCancellation`)
- `ignoreAudioUntilMs` existe mais doit être passé par le composant appelant
- Aucune coordination entre fin de lecture .wav et réactivation de la VAD
- Aucun équivalent du COOLDOWN serveur

Si l'utilisateur utilise le pipeline 1, l'anti-écho est instable par construction.
Si l'utilisateur utilise le pipeline 2, l'anti-écho est beaucoup plus solide.

**Confusion probable : l'utilisateur passe d'un pipeline à l'autre sans s'en rendre compte.**

#### Symptôme 4 — Lenteur

**Causes cumulables :**

| Cause | Localisation | Impact |
|---|---|---|
| Kokoro timeout 30s avant fallback | voice_sidecar_app.py | +30s si Kokoro bloque |
| asyncio.Lock() séquentialise TTS | voice_sidecar_app.py | pipeline 2 attend pipeline 1 |
| _ensure_model() au premier STT | faster_whisper.py | 5–30s de latence initiale |
| health check toutes les 20s | useSpeech.ts ligne 123 | peut déclencher _ensure_model |
| WebRTC frame-by-frame playback | audio_utils.py + runtime.py | asyncio.sleep(0.02) × N frames |
| STT synchrone (blocking thread) | api_routes.py ligne 769 | pas d'async natif sur les backends |

---

#### Symptôme 5 — Erreur de synchronisation

**Le backend ne sait pas quand le navigateur a fini de jouer le fichier .wav.**

Dans le pipeline 1, le flux est :
1. Backend génère le .wav, le sert à `/api/voice/audio/{file}`
2. Navigateur fait GET du fichier et le joue
3. **Backend ne reçoit aucun événement "lecture terminée"**
4. La VAD JS peut se réactiver immédiatement après que le navigateur a commencé à jouer (pas fini)

Dans le pipeline 2, c'est l'inverse : l'audio est envoyé frame par frame via WebRTC, et `_last_audio_play_end_at` est mis à jour après le dernier frame. La synchronisation est précise.

### Solution proposée par Claude

**Claude ne propose aucune modification directe. Ces propositions sont à comparer avec Codex.**

**Stratégie prudente en 3 phases :**

**Phase 0 — Isolation du problème (priorité absolue avant tout fix)**

Identifier d'abord quel pipeline est utilisé quand le bug se produit.
Ouvrir les DevTools réseau et regarder si les requêtes passent par :
- `/api/voice/speak` + `/api/voice/audio/` → pipeline 1 actif
- connexion WebRTC → pipeline 2 actif
- les deux → c'est le problème principal

Ne jamais lancer les deux pipelines simultanément pour un test.

**Phase 1 — Fix minimal à faible risque (pipeline 1 uniquement)**

Fix A : `useSpeech.ts` lignes 185 et 551
```ts
// Avant :
getUserMedia({ audio: true })
// Après :
getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true } })
```
Risque : faible. Retour arrière : 2 lignes.

Fix B : Réduire le Kokoro timeout dans le sidecar
`OPENJARVIS_KOKORO_TIMEOUT=12` (au lieu de 30s) pour que le fallback Piper intervienne plus vite si Kokoro est bloqué, ou au contraire le désactiver pour forcer Kokoro.

**Phase 2 — Décision d'architecture (nécessite Ruth + Codex)**

Question principale : **quel pipeline est le bon pour la V1 stable ?**
- Si pipeline 1 (navigateur) → le WebRTC POC doit être isolé et jamais lancé en même temps
- Si pipeline 2 (WebRTC) → le pipeline 1 doit être désactivé ou réservé à un mode fallback
- Si les deux doivent coexister → il faut un mécanisme d'exclusion mutuelle du sidecar

Ce choix ne peut pas être fait par Claude seul. Il implique l'architecture globale de Jarvis.

**Phase 3 — Fixes profonds (seulement après décision Phase 2)**

- Coordination TTS/STT dans le pipeline 1 (état `isSpeaking`, event `audio.ended`)
- Isolation du sidecar par pipeline (deux instances sur des ports différents)
- Thread-safety des globals dans `voice_proxy_routes.py`
- Préchargement de faster_whisper au démarrage plutôt qu'en lazy load
